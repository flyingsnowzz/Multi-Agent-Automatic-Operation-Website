# 今日工作总结：文章评分 Agent 开发与调研

日期：2026-06-23

## 1. 今日目标

今天主要围绕“文章评分 Agent”进行开发和调整，目标是让系统能够从 SQL 爬虫数据中读取文章，对每篇文章进行质量评分，并把评分结果写回新的 SQL 结构中，为后续的选题、调研、改写和发布流程提供依据。

整体目标从早期的“topic 排名”逐步收敛为：

- 不再做 topic 排名。
- 聚焦文章本身评分。
- 使用 AI 判断文章质量、重要性、通知属性等主观维度。
- 使用代码处理字数、时间、数据库写入等确定性逻辑。
- 最终把每篇文章的评分结果和维度分数写入新的 SQL 文件或数据库结构。

## 2. 已完成的主要工作

### 2.1 重新定义文章评分维度

当前文章评分系统已经从最初的 topic 贡献度模式，调整为文章质量评分模式。

目前核心维度包括：

| 维度 | 权重 | 评分方式 | 说明 |
| --- | ---: | --- | --- |
| 标题质量 | 25% | AI 评分 | 判断标题是否新颖、具体、有传播价值 |
| 内容重要程度 | 50% | AI 评分 | 判断文章本身是否有新闻价值、政策价值、故事价值或用户关注价值 |
| 文章长度 | 10% | 代码评分 | 根据文章字数计算，弱惩罚，避免过短或过长 |
| 时效性 | 10% | 代码评分 | 根据发布时间计算，越近越高 |
| 是否通知 | 5% | AI 判断 + 代码转换 | 通知类文章分数较低，新闻/故事/研究/人物类更高 |

其中，内容重要程度会受到时效性影响。较新的文章重要性保留更多，较旧的文章会进行衰减。

### 2.2 修改时效性规则

根据今天的讨论，时效性规则调整为：

- 2 个月以内：不单独统计时效分，重要性系数为 1。
- 6 个月以内：时效分约为 80%-100%，重要性系数为 0.8。
- 12 个月以内：时效分约为 60%-80%，重要性系数为 0.5。
- 24 个月以内：时效分约为 30%-60%，重要性系数为 0.5。
- 24 个月以后：重要性系数为 0.1。

这个规则解决了一个关键问题：有些文章本身很重要，但如果时间太久，对当前选题和发布的价值会明显下降。

### 2.3 调整文章长度惩罚

文章长度评分已经改为弱惩罚逻辑。

原因是文章长度只占总分 10%，不应该因为文章短或长就严重拉低总分。当前目标是让长度评分均值大约在 60 分左右，标准差大约在 10 分左右，用来做轻微修正，而不是作为主要判断依据。

### 2.4 增加通知类文章判断

新增 `is_notice` 判断。

如果文章是通知、公告、流程提醒、招生提醒等偏事务类内容，系统会降低其评分；如果是新闻、研究成果、人物故事、教授经历、学生成长、项目进展等内容，则更容易获得高分。

这个规则符合当前业务目标：系统更关注适合传播、改写、发布的新闻和故事类内容，而不是纯通知类内容。

### 2.5 加强故事类内容评分标准

今天特别补充了一个重要规则：

故事类文章也可以获得高分。

例如：

- 教授的研究经历或心路历程。
- 学生、校友的成长故事。
- 项目团队从失败到成功的过程。
- 学术成果背后的故事。
- 有人物、有冲突、有情绪、有传播价值的内容。

这类内容即使不是政策或重大新闻，也可能非常适合用户阅读和平台传播，因此在 AI prompt 中已经明确加入了该规则。

## 3. AI 接入情况

目前评分系统已经可以接入 DeepSeek API。

AI 主要负责判断主观维度：

- 标题质量分。
- 内容重要性分。
- 是否为通知类内容。
- 评分理由。

代码负责处理确定性维度：

- 文章长度分。
- 时效分。
- 重要性时效衰减。
- 综合分计算。
- SQL 写入。

如果没有 API，系统之前支持空值或 fallback；现在主要方向已经调整为尽量使用 AI 完成主观评分，避免规则硬编码过多。

## 4. 数据库写入能力

今天已经实现了文章评分结果写回 SQL 的能力。

相关文件包括：

- `sql/alter_crawler_article_scores.sql`
- `sql/alter_crawler_article_scores_v2_notice_freshness.sql`
- `agents/scoring_agent/tools/article_score_writer.py`

设计原则是：

- 不直接破坏原始 `crawler_data.sql`。
- 使用新的 alter SQL 文档添加评分字段。
- 每篇文章通过原始文章 ID 或唯一标识与评分结果一一对应。
- 评分结果可以写入新的 SQL 文件，方便后续导入数据库。

这样可以保留原始数据，同时让评分系统生成结构化结果。

## 7. 同事代码逻辑调研

今天也简单查看了同事已有代码。

同事主要搭建的是从 crawler 到后续 Agent 的完整流水线：

```text
crawler 文章
```

主要涉及文件：

- `workflows/crawler_workflow.py`

结论是：同事做的是工作流骨架和任务流转，你今天做的文章评分系统可以作为 crawler 分流阶段的核心评分模块接入进去。

## 8. 当前系统定位

当前文章评分 Agent 的定位可以总结为：

> 从爬虫数据库中读取文章，使用 AI 和规则对每篇文章进行综合评分，并将评分结果结构化写回数据库，为后续选题、调研、改写、发布流程提供排序和分流依据。

它不是最终发布 Agent，也不是调研 Agent，而是整个多 Agent 系统中的前置筛选与质量判断模块。

## 9. 下一步建议

下一步可以做三个方向：

### 9.1 接入 crawler 分流流程

把文章评分结果接入 `crawler_workflow.py` 的决策逻辑中。

例如：

- 高分文章进入 `publish_candidate`。
- 中分文章进入 `rewrite_candidate`。
- 低分文章进入 `discard` 或低优先级池。

### 9.2 做 ResearchAgent

如果继续往后做，下一个比较合理的 Agent 是 ResearchAgent。

它的作用是：

- 读取高价值文章。
- 补充背景信息。
- 总结核心事实。
- 生成改写材料。
- 给 WriterAgent 提供结构化 brief。

### 9.3 继续校准评分权重

需要多抽几篇真实文章人工阅读，对比 AI 分数和人工判断。

重点观察：

- 故事类文章是否被低估。
- 通知类文章是否被高估。
- 旧文章是否被合理惩罚。
- 短但重要的文章是否被误伤。
- 标题党文章是否被过度加分。

之后再微调权重和 prompt。
